# Independent adversarial audit — TOHSENO contract generation 0.8.0

## Auditor identity and limitations

- **Auditor:** GPT-5.6-Sol (`xhigh` reasoning), invoked as an independent
  read-only Codex sub-agent.
- **Date:** 2026-07-31 (America/Santiago).
- **Limitation:** This is an AI-assisted source audit, not formal verification,
  a human audit, or a warranty.
- **Safety:** The auditor used clean temporary Git archives and read-only
  commands. It did not change the shared worktree, query live RPCs, access
  credentials, sign or broadcast transactions, or make payments.

## Recommendation

**NO-GO for production deployment or activation in the current state.**

The frozen Solidity code has no identified Critical or High authorization
defect and can continue through review and canary preparation. Deployment is
blocked by the unresolved Medium operational CREATE2/pre-activation-state risk,
the repository's unmet external-review and authority prerequisites, and the
absence of a fresh ceremony-time EIP-7951 gate.

### M-01 — Public CREATE2 coordinates permit candidate griefing and pre-activation state

The canonical singleton CREATE2 deployer is permissionless, while both salts,
init code, and resulting addresses are public. Anyone can submit the exact
factory or registry deployment before the authorized payer.

An attacker cannot substitute different runtime code at either address, but
can occupy the frozen address with the exact code, make the planned payer's
CREATE2 attempt fail, and use the registry before activation. Runtime equality
alone would then be insufficient evidence of deployment provenance or clean
pre-activation history.

The prepared ceremony correctly stops when target code is nonempty, but that
detects rather than prevents the event. The registry is permissionless and
stateful as soon as it exists. Unexpected exact-code predeployment therefore
requires an explicit policy: abandon the coordinates, or verify and explicitly
admit exact deployment provenance and all state/event history under an accepted
activation rule. Official-payer provenance cannot be assumed from bytecode.

**Recommendation:** do not activate from address/runtime equality alone. Define
authoritative behavior for unexpected predeployment and pre-activation state,
including deployment transaction, receipt, event history, activation-block
filtering, and the disposition of state written before activation. If official
deployment provenance is mandatory, use a new generation/topology with an
authenticated or genuinely exclusive deployment path.

### L-01 — A transfer can impose an unsolicited controller association

`transferShot` authenticates the current controller but does not require a
signature from the new controller. An attacker can register its own Shot and
transfer it to a victim BuilderAccount. The attacker loses mutation authority,
but naïve indexers could misrender the resulting controller as creation or
endorsement by the victim. Transfer to a deployed non-ERC-1271 contract also
freezes future mutation.

**Recommendation:** clients must distinguish current mutation authority from
recipient endorsement and mark inbound transfers unaccepted until the new
controller signs a later action. A future generation may use a two-phase or
dual-signature transfer if consent is required.

### L-02 — Rust action validation accepts unusable coordinate combinations

`BuilderAccountActionV2::digest` checks a nonzero action account and a valid
BuilderAccount domain but does not require the action account to equal the
domain's `verifying_contract`. The contract always hashes `address(this)` in
both positions. A mismatched Rust action can therefore be signed but can never
be accepted by either named contract.

The Rust validator also permits a new recovery address equal to the action
account, while the contract rejects itself as a recovery authority. The impact
is failed signing/relay interoperability rather than unauthorized execution.

**Recommendation:** make the normative validation rule explicit, enforce
account/domain equality, reject self-recovery, and add negative Rust and
cross-language vectors.

### Informational findings

- Dynamic `bytes memory` allocation after ERC-1271 `staticcall` permits a
  hostile selected controller/recovery authority to burn the relayer's gas.
  That authority can already refuse its own action. A bounded 32-byte copy is a
  future hardening option.
- Generic ERC-1271 behavior permits a PROTOCOL key to validate any digest it
  deliberately signs. The signing client must expose only typed TOHSENO
  purposes.
- The direct chain probe and mock-backed wrapper tests did not, in combination,
  prove the wrapper's exact five-word layout against the live precompile.
  Manual review found `digest,r,s,x,y` correct. The coordinating session added
  a test that checks all five official-vector words; the real deployed-wrapper
  canary remains required.

## Positive security conclusions

- P-256 point, scalar, and low-s validation is correct; the precompile input is
  ordered `digest,r,s,x,y`; missing/malformed/non-one output fails closed.
- EIP-712 domains bind the live chain and verifying contract, and typed actions
  bind their relevant state coordinates.
- Device and recovery nonces are separate and correctly advanced; recovery
  finalization invalidates the prior device epoch and outstanding device
  actions in constant time.
- Strict `v` and low-s rules close secp256k1 malleability in recovery.
- Factory front-running produces the same constructor-bound BuilderAccount and
  grants no caller authority.
- Registration windows and duplicate-commit behavior match the specification.
- Registry append and transfer share a nonce and bind the head and checkpoint
  sequence, preventing replay, gaps, and stale transitions.
- The contracts have no owner, proxy, upgrade hook, pause, delegatecall,
  selfdestruct, arbitrary execution, fee, or token custody.

## False-positive dispositions

The auditor agreed with the internal preaudit that:

- Factory `abi.encodePacked` is unambiguous because invariant creation code is
  followed by fixed-width ABI constructor data.
- Strict equality for magic values, precompile integer one, zero identifiers,
  and return length is intentional.
- Recovery `ecrecover` uses strict `v` and low-s, while replay identity does not
  depend on signature bytes.
- Timestamp use is required for deadlines, commitment maturity, and recovery.
- Relaying and permissionless account deployment confer no `msg.sender`
  authority.
- Arbitrary ERC-1271 controllers and lack of registry-side BuilderAccount code
  pinning are deliberate neutrality boundaries.
- A registry cannot validate ancestry-free checkpoint content from a `bytes32`
  head; that remains an off-chain conformance boundary.

No Slither/Aderyn disposition in the preaudit was shown to be wrong. The
material omission was that factory front-run idempotence does not by itself
close top-level registry predeployment and pre-activation state.

   exact-code predeployment and pre-activation state are handled.
2. Complete the accepted independent-review gate and disposition every
   Critical, High, and Medium finding.
3. Rebuild with the exact pinned compiler and Foundry profile.
4. Immediately before signing, run the full positive/negative/infinity and
   exact-6,900-gas EIP-7951 gate against one rechecked canonical block at the
   explicit RPC.
5. Verify chain 4663, deployer runtime, target state, exact sender/to/value/
   calldata, receipts, event history, and resulting runtime bytes.
6. Run the deployed-wrapper P-256 canary and real three-day recovery flow.
7. Establish and independently pin the release-authority policy digest and
   threshold-signed activation ordering.
8. Make clients reject unadmitted pre-activation evidence, classify generic
   controllers as neutral, validate checkpoint provenance, and avoid treating
   unsolicited transfers as recipient endorsement.
9. Keep deployment unavailable until the repository accepts and independently
   reviews a narrow ceremony.
