## Preliminary findings

No critical, high or medium-severity vulnerability was identified in this
pass. This conclusion is limited by the methods above and must be challenged by
independent reviewers.

Slither's strict-equality reports are required exact checks for ERC-1271 magic
and zero/specific identifiers. Its missing-zero-check reports are false
positives because both recovery entry points call `_checkRecoveryAuthority`
before assignment. Timestamp reports correspond to explicit deadlines,
commitment windows and the three-day recovery delay. Assembly, low-level call
and long-literal reports identify reviewed implementation boundaries already
covered by the P-256, ERC-1271, EIP-7702 and curve-constant tests. No detector
output was dismissed solely because the test suite passed.

Aderyn's high `abi.encodePacked` collision report targets the factory's exact
CREATE2 init-code concatenation. The first segment is invariant compiled
creation code and the only variable segment is fixed-width `abi.encode` of two
`uint256` constructor arguments, so no competing input tuple can move the
boundary. Using `abi.encodePacked` is required to reproduce the bytes deployed
by `new BuilderAccount{salt: salt}(initialX, initialY)`. Its `ecrecover`
malleability report is mitigated by strict `v` and low-s enforcement before
recovery, and recovery signatures are not keyed or deduplicated by raw
signature bytes. Its state-address reports are false positives because
`_checkRecoveryAuthority` rejects zero and self before both assignments. The
remaining public-function and single-use-internal-function reports are API and
style suggestions, not security findings.

### I-01 — Registry acceptance is intentionally broader than TOHSENO identity

Severity: informational; design boundary.

`ShotRegistry` accepts any deployed, non-EIP-7702 controller that returns exact
ERC-1271 magic. The registry alone therefore cannot prove that a controller is
an approved TOHSENO BuilderAccount. This is intentional neutrality, but every
client, explorer and node must apply the activated-generation runtime policy
before presenting a controller as a TOHSENO BuilderID.

Recommendation: keep this boundary prominent in receipts and user-facing
rendering; add production integration tests proving that a generic ERC-1271
controller can register neutrally but is not classified as an approved
BuilderID.

### I-02 — ERC-1271 calls use dynamically allocated return data

Severity: informational; authority-controlled denial of service.

The recovery-authority and registry-controller checks use high-level
`staticcall` and allocate the complete returned byte array before requiring an
exact 32-byte result. A deliberately hostile selected authority could consume
gas with large return data. That authority can already refuse all signatures,
so this does not create a new privilege or let a third party block an honest
authority, but bounded 32-byte assembly calls would reduce griefing surface.

Recommendation: ask independent auditors whether bounded return-data copying
is worth a successor-generation change. Do not mutate frozen generation 0.8.0
in place.

### I-03 — ERC-1271 protocol permission is not digest-domain restricted

Severity: informational; integration discipline.

An authorized protocol key can produce valid ERC-1271 results for any digest
it deliberately signs. The account does not execute calls or custody value,
and TOHSENO actions are independently domain-separated, so no direct exploit
was found. Integrators must not describe the account as a general-purpose
transaction smart wallet or ask the device key to sign opaque external
digests.

Recommendation: keep signing UI and helper APIs closed over typed TOHSENO
actions; add negative integration tests that refuse unknown signing purposes
before reaching the contract.

### I-04 — Production safety depends on the external EIP-7951 gate

Severity: operational prerequisite; deployment blocker if absent.

The verifier deliberately fails closed when `0x100` is missing or returns a
non-exact value, but the contract cannot distinguish an absent precompile from
an invalid signature. The fresh positive, negative, infinity-edge and exact
6,900-gas probe is therefore part of the security boundary.

Recommendation: keep the probe synchronous with the one-time production
ceremony, bind it into activation evidence, and refuse cached observations.

## Disposition

Generation 0.8.0 remains inactive, undeployed and deployment-unauthorized. The
next permitted steps are external AI review, independent human/competitive
review, finding disposition, release-authority policy creation and explicit
human authorization of a successor production ceremony. Source remediation
must create and re-audit a new immutable generation.
