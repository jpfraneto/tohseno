Make the idea exist

bun install --frozen-lockfile
bun run tohseno

Source preview: this checkout implements the prepared, unpublished 0.5.0 release. No installer, package, tag, or deployment has been published for it.

On an empty contact sheet, write one intention. With existing shots, choose Take another Shot or Evolve a Shot. An Evolution changes the same coherent intention; it does not create another Shot. Every app lands as an independent repository under your configured shots directory—~/tohseno/shots by default. TOHSENO uses the selected Codex or Claude Code provider to propose a sanitized plan, then shows the app, template, skills, data, generated-app runtime identity, and definition of done before building.

The raw intention stays private and gitignored. For an explicit local input, use one UTF-8 Markdown file and repeat --reference for image references:

bun run tohseno -- create --file intention.md --reference sketch.png

The file paths are ordinary local inputs; their private contents never enter shell arguments, the factory release, Git history, or centralized logs.

One Shot can evolve

bun run tohseno -- evolve <shot>
bun run tohseno -- status <shot>

A Shot is one coherent software intention. An Evolution changes that same Shot and keeps its stable identity and repository. Starting another intention creates another Shot.

Distribution uses exactly three protocol states: EVOLVING means the Shot is not represented as publicly downloadable, PUBLISHED means downloadable through TOHSENO from published source, and APP_STORE means shipped through Apple. Evolutions can be recorded in every state; repository creation, build readiness, and app runtime state are separate.

Optional Builder-signed public records can describe Evolutions and lifecycle transitions. A signature makes the declared claims portable and verifiable as that Builder key’s attestation; it does not independently prove ownership or select between competing histories. A replaceable node can index one accepted history, but production trust roots and cross-node fork resolution remain Open. Local creation and use require no node, account, server, wallet, chain, or TOHSENO mobile app. The mobile app is intentionally absent until the first stable factory release creates it as that release’s first Shot.

One factory, multiple doors

bun run tohseno -- studio
bun run tohseno -- studio --port 4747 --no-open

Studio is a local browser contact sheet for the same configured shots directory used by the CLI. It binds to 127.0.0.1, never the LAN, and watches that directory for shots created through either door. Its creation form accepts a long intention, one optional Markdown file, and optional image references.

Studio opens through a mode-0600 temporary launcher file. Its one-time fragment establishes an HTTP-only, path-scoped local session and is removed from browser history immediately. The shell, command line, and printed base URL contain no reusable session credential; private reads and mutations require the session.

The terminal and Studio call the same planner and deterministic composition engine. They share the released kernel/template/skill catalog, concurrency-safe allocation, atomic repository creation, independent Git history, private provenance, and verification. Studio is not a daemon requirement: close it and the same shots remain available through the source CLI’s list, verify, and open commands.

What the agent operates

Every new Shot pins its operational playbook, app manifest, composition lock, app-skill instructions, verifier, and machine commands locally. Apps build and launch directly from the Xcode project, scheme, and product declared in that manifest; they do not inherit a backend or account system.

Run the real Simulator

bun run tohseno -- run <shot>
bun run tohseno -- preview <shot>
bun run tohseno -- doctor

On macOS with Xcode command-line tools and an available iPhone Simulator, run builds, installs, and launches the shot in Apple Simulator, then attempts a private contact-sheet capture. A failed capture does not stop an otherwise running app.

preview adds an interactive local browser stream of that same native Simulator; it is not an in-browser iOS emulator. Interactive preview additionally requires Apple Silicon, a native arm64 Node.js 20 or newer, and the pinned serve-sim helper. Simulator use does not require paid Apple Developer Program membership. doctor reports the selected Node architecture and exact readiness, and unsupported preview does not disable Studio’s contact sheet, creation, or ordinary CLI verification.

The point

The prototype is the payoff: a real native app in iPhone Simulator that you can use, change, keep, or leave on the contact sheet. Most shots miss. That is why you can take a lot of them. TOHSENO makes no promise of riches and never turns financial plumbing into the reason to build.

What stays local

A shot has its own Git history, SwiftUI app, manifest, exact composition lock, app skills, tests, landing page, verifier, operations, and release provenance. The neutral kernel contains no writing, identity, analytics, auth, or backend assumption. Installed capabilities are declared and verified.

When create --file or Studio receives private creation input, its normalized intention, reference copies, hashes, original filenames, options, and structured events stay in the shot’s gitignored .tohseno/provenance/ directory. Temporary Studio uploads are removed after the job finishes or stops safely. After every coding-agent exit—including a failed one—the verifier rejects copied private input, unsafe links, changed pinned rails, and missing ignore rules. A result that fails that gate is moved to an explicitly unsafe hidden path instead of being presented as a ready shot.

Studio does not upload shots or creation input to TOHSENO. The selected coding agent can read creation input to do the requested work and handles it under that provider’s own privacy, retention, and account settings.

New apps start local and account-free unless the accepted manifest declares otherwise. Every shot builds without TOHSENO credentials or a live factory.

Approval boundary

The agent can diagnose and prepare locally. It must ask before creating accounts, spending money, handling credentials, changing DNS, publishing packages, deploying production, or submitting to an app store. The canonical machine exposes no deployment or store-submission command.

Current production boundary

The factory prepares local source, Simulator builds, verification, and an independently owned static landing page. Broad VPS provisioning, deployment, monitoring, recovery, DNS changes, publishing, and store submission are not implemented by the canonical machine operations.

iOS is the only implemented app platform. Android and web do not appear as fictional choices. Linux can run the factory and API, but only macOS with Xcode can build and launch the iOS app.

Ownership and ejection

Remove the global CLI and an existing shot still has its source, generated Xcode project, manifest, composition locks, tests, pinned verifier and machine protocol, and runbooks. No symlink points back to a factory cache. Identifiers, data paths, production references, and the static landing page remain with the shot.

Advanced and automation use

The prepared source CLI exposes create, evolve, status, list, open, doctor, verify, run, preview, and studio. The detailed machine protocol is documented in each Shot at .tohseno/OPERATIONS.md and in the repository.
